## Treatments

| ID | Threat | Proposed outcome | Alternatives |
|---|---|---|---|
| TR-001 | T-001 | Every state-changing request made with the session cookie is accepted only when it demonstrably comes from the application's own origin and is a JSON request. Keep SC-015 and SC-013 as specified and prove them on every non-GET route. | Per-request anti-CSRF token; Rely on SameSite alone (rejected by SC-015's own sources) |
| TR-002 | T-002 | Ceremony routes get the same origin and content-type gate as authenticated routes, and a challenge can be completed only by the browser that requested it, exactly once. | Bind the challenge through a short-lived pre-session cookie; Return an opaque ceremony ID that the same page must present; Leave ceremony routes ungated and rely on WebAuthn origin checks only |
| TR-003 | T-003 | Requests from other origins, or addressed to another host name, are refused before they count against the sign-up and login allowance, so another page cannot spend the user's attempts. | Key the limit on something a cross-site page cannot share (not available without storing visitor data); Accept the lockout risk for a single-user localhost demo |
| TR-004 | T-004 | An internal user ID is unguessable, is never issued twice, and an admin-list entry that matches no current user is reported at startup, so admin authority cannot pass to a later sign-up. | Identify admins by a passkey credential instead of a user ID; Remove deleted admins from configuration by procedure only |
| TR-005 | T-005 | Each route accepts exactly one kind of credential. Bearer tokens work only on the link operations of FR-5.2; account, passkey, token-management and admin routes accept only a session; a request carrying both is refused. | Scoped tokens with per-token permissions (more than the demo needs); Allow tokens on admin routes for admin users |
| TR-006 | T-006 | Every link operation binds the caller, the link's owner and the action in the Links module, and every admin operation checks the configured role, whichever credential is used. Keep SC-016 and SC-021 and prove them per operation. | Check ownership in each route (rejected by DR-2) |
| TR-007 | T-007 | User-supplied titles and URLs stay inert text in every view, including the admin list, confirmation dialogs and tooltips. Keep SC-009 and SC-010 and prove them in the privileged views. | Server-side stripping of markup (not needed if rendering is inert) |
| TR-008 | T-008 | What is stored and shown for a target is the parsed, normalized URL, so the visible host is the real destination. Targets with embedded credentials are refused, and titles cannot carry control or direction-override characters. | Show a warning badge on unusual URLs instead of refusing them; Strip, rather than refuse, embedded credentials and control characters |
| TR-009 | T-009 | Before the system is reachable by anyone outside the team, the owner decides how sign-up and link targets are constrained (for example invitations, a warning page before leaving, or an allow-list). Until then the system stays on localhost. | Invite-only sign-up; Interstitial page before redirecting; Target domain allow-list; Accept the abuse risk and rely on admin deletion |
| TR-010 | T-010 | The own-domain rule compares normalized host names and treats every name for the local machine as the site itself while the site runs on localhost, so a link cannot point back at the service. | Detect loops at redirect time instead; Compare full origins (host and port) only |
| TR-011 | T-011 | API calls that present no valid token share the address-keyed allowance used for login, and each kind of denial event has a per-minute ceiling with a count of suppressed events, so an anonymous caller can neither bypass the limit nor flush audit evidence quickly. | Write audit-required events to a separate file with its own retention (needs an owner decision on OD-004/OD-005); Stop emitting an event per unknown token |
| TR-012 | T-012 | The owner decides whether unlimited anonymous redirects, each with a synchronous write, are acceptable for the demo or whether the write cost per request must be bounded. Click-count inflation stays accepted under FR-3.7. | Accept for the localhost demo; Bound redirect load without storing visitor data (a global ceiling); Decouple counting from the request path |
| TR-013 | T-013 | Short codes are drawn from a cryptographic random source with every character equally likely, so codes cannot be predicted from earlier ones. | Longer codes (changes FR-2.7) |
| TR-014 | T-014 | Deleting an account removes or revokes the user, passkeys, sessions, tokens and links as one all-or-nothing change, and a request that started before the deletion cannot act for the account after it. | Ordered steps with compensating cleanup at startup |
| TR-015 | T-015 | The owner decides how an account holder can detect and undo an unwanted passkey, and whether adding a passkey, creating a token or deleting the account needs a fresh passkey check. | List and remove passkeys on the account page; Require a fresh passkey assertion before sensitive account actions; Both; Accept for the demo; the event file is the only record |
| TR-016 | T-016 | Authenticated responses, above all the one-time token, are never stored by the browser, so nothing remains readable after sign-out. | Mark only the token response |
| TR-017 | T-017 | The localhost-only decisions are named in one place and block any other deployment until the owner has decided transport security, proxy trust, the rate-limit key and exposure of open sign-up. | Fail startup when the configured origin is not localhost; Document only |

## Proposed requirements

- **RQP-001**: Internal user IDs are never reused, including after account deletion. (T-004)
- **RQP-002**: A target URL that contains embedded credentials is rejected with a reason. (T-008)
- **RQP-003**: A title that contains control or direction-override characters is rejected with a reason. (T-008)
- **RQP-004**: The own-domain rule covers every name that reaches the service itself. (T-010)
- **RQP-005**: API tokens are accepted only for the link operations of the JSON API. (T-005)
- **RQP-006**: API calls without a valid token are limited per network address like sign-up and login. (T-011)
- **RQP-007**: Account deletion is all-or-nothing. (T-014)
